# AI Construction Compliance Platform — Draft de especificaciones MVP v2 (BC)

## 1. Propósito del documento

Este documento redefine el MVP con foco en British Columbia para que pueda pasar a implementación en Kiro con una base más sólida de producto, arquitectura y decisiones de cumplimiento. El objetivo es evitar que el sistema nazca como un conjunto de features aisladas y, en cambio, estructurarlo como un motor de decisiones auditable para acceso, cumplimiento y hallazgos de seguridad.

El producto no debe plantearse como un simple checklist tool ni como una app de computer vision. La tesis correcta del producto es: **regulatory reasoning engine for construction operations**, con una primera aplicación clara en acceso a obra, elegibilidad de trabajadores, evidencia visual y decisiones explicables.

## 2. Product thesis

### 2.1 Qué es el producto

Una plataforma SaaS para construction operations orientada al mercado de BC que unifica:

- worker identity and access validation
- certification and site eligibility management
- QR/SMS-based check-in and gate workflows
- visual safety compliance analysis from field evidence
- audit-grade compliance decisions with explainability

### 2.2 Qué no es

No es solamente:

- un repositorio de certificados
- un sistema de QR para entrada
- una app de detección PPE
- un formulario digital de inspecciones

### 2.3 Definición correcta

Es un **Compliance Decision Platform** con cuatro pilares:

1. Identity and eligibility
2. Site policy enforcement
3. AI-assisted safety observation
4. Audit and regulatory explainability

## 3. Killer workflow del MVP

El MVP debe centrarse en un workflow diario y repetible, no en una colección suelta de módulos.

### 3.1 Killer workflow inicial

**Morning site access validation + daily hazard scan + end-of-day compliance summary**

### 3.2 Flujo operativo

1. Worker llega a site.
2. Escanea QR persistente o recibe link por SMS.
3. El sistema valida identidad, certificaciones, site policies y estado de acceso.
4. Se emite una decisión explicable: allowed / conditional / denied.
5. Durante la jornada, supervisor o CSO sube fotos de obra.
6. El sistema genera hallazgos con explicación, regla aplicada y acción correctiva sugerida.
7. Al final del día, el sistema genera un resumen auditable por site.

### 3.3 Por qué este workflow importa

Este flujo crea hábito diario, hace el producto sticky y conecta acceso, operación y compliance en un ciclo cerrado. También genera datos que fortalecen el moat: historial de elegibilidad, evidencia visual, decisiones explicables y patrones de riesgo por site.

## 4.3 AI Safety module (redefinido)

El módulo AI no puede quedarse en “PPE detection + fall risk + manual review”. Para ser diferenciador necesita tres capas explícitas.

### Layer 1 — Detection layer

Detecta objetos o evidencias observables.

Ejemplos:

- helmet
- vest
- harness
- ladder
- scaffold
- trench / excavation edge
- roof edge
- machinery proximity
- blocked exit / clutter

Output ejemplo:

```json
{
  "detections": [
    {"type": "worker", "confidence": 0.98},
    {"type": "roof_edge", "confidence": 0.92},
    {"type": "harness_missing", "confidence": 0.84}
  ]
}
```

### Layer 2 — Scene understanding layer (crítica)

Convierte detección en contexto operacional.

Ejemplos:

- work at height scenario
- roofing activity detected
- excavation context
- framing activity
- ladder access scenario
- material handling near mobile equipment

Output ejemplo:

```json
{
  "scene": "roofing work at height",
  "activity": "worker installing roof framing",
  "risk_context": "fall exposure near unprotected edge",
  "confidence": 0.87
}
```

### Layer 3 — Regulatory mapping layer

Toma scene + detections + metadata y lo mapea a reglas regulatorias o site policies.

Inputs:

- detection layer output
- scene understanding output
- site metadata
- jurisdiction
- active policy version

Output ejemplo:

```json
{
  "potential_violation": true,
  "regulatory_basis": ["WorkSafeBC_fall_protection_rule"],
  "site_policy_basis": ["SitePolicy_v3:working_at_heights"],
  "severity": "high",
  "suggested_action": "Stop work and verify fall protection controls"
}
```

### Principio clave

Sin scene understanding + regulatory mapping, el sistema se percibe como una app de computer vision genérica. Con estas tres capas, el producto se convierte en una plataforma de regulatory reasoning asistida por AI.

## 4.7 Real-time enforcement loop (nuevo obligatorio)

El sistema no debe detenerse en una decisión. Debe cerrar el loop operativo hasta llegar a una acción ejecutable y trazable en sitio.

### Problema que resuelve

Hoy el flujo llega a:

- access decision
- AI finding
- reporting

Pero en un entorno real de obra eso no es suficiente. El sistema debe responder qué pasa inmediatamente después de una decisión crítica, especialmente en gate scenarios o hallazgos de alto riesgo.

### Objetivo

Traducir decisiones de compliance en enforcement actions concretas, con escalación, override controlado y posibilidad de re-validación.

### Enforcement states sugeridos

#### Para acceso

- allowed
- conditional_allow
- denied_pending_fix
- denied_escalated
- manually_overridden
- revalidation_required
- revalidated_allowed

#### Para findings

- logged
- corrective_action_required
- supervisor_acknowledged
- stop_work_recommended
- escalated_to_cso
- fix_submitted
- reinspection_required
- closed

### Enforcement actions mínimas del MVP

- deny entry
- notify supervisor
- request updated certification or proof
- require manual review at gate
- trigger override workflow
- create corrective action task
- require re-scan or re-validation
- escalate to CSO / site admin

### Componentes mínimos

#### EnforcementAction

Representa la acción operativa resultante de una decisión.

Campos sugeridos:

- id
- decision_record_id
- action_type
- subject_type
- subject_id
- site_id
- status
- assigned_to
- due_at
- executed_at
- resolution_notes
- created_at

#### OverrideRequest

Representa una excepción solicitada a una decisión automática.

Campos sugeridos:

- id
- decision_record_id
- requested_by
- reason_code
- freeform_reason
- evidence_asset_id
- status
- approved_by
- approved_at
- expires_at

#### RevalidationAttempt

Representa un nuevo intento de validación después de una corrección o excepción.

Campos sugeridos:

- id
- original_decision_id
- triggered_by
- trigger_type
- context_json
- new_decision_id
- created_at

### Flujo mínimo de enforcement en gate scenario

1. Worker solicita acceso.
2. Compliance Decision Engine devuelve denied o conditional.
3. El sistema crea `EnforcementAction`.
4. Se notifica al supervisor o gate operator.
5. El trabajador ve razones y acción requerida.
6. Si se corrige el problema, se dispara `RevalidationAttempt`.
7. Si se necesita excepción, se crea `OverrideRequest`.
8. Toda resolución queda auditada.

### Ejemplo de output extendido

```json
{
  "decision": "denied",
  "decision_type": "site_access",
  "reasons": [
    "Fall protection certification expired 12 days ago"
  ],
  "rules_applied": [
    "SitePolicy_v3:fall_protection_required"
  ],
  "enforcement": {
    "action": "deny_entry_and_notify_supervisor",
    "next_step": "worker_must_upload_valid_certification_or_request_override",
    "revalidation_allowed": true,
    "override_allowed": true
  }
}
```

### Reglas clave

- una decisión crítica debe poder generar una acción operacional inmediata
- override nunca reemplaza la decisión original; crea una capa de excepción auditada
- toda corrección relevante debe permitir re-validación explícita
- gate decisions deben reflejar el estado más reciente, no una copia cacheada obsoleta

## 9. Business rules esenciales

## 9.1 Access rules

- una identidad válida no implica acceso válido
- acceso depende de evaluación actual del Compliance Decision Engine
- toda decisión de acceso debe poder justificarse con reglas y evidencia
- access tokens de corta vida deben ser revocables
- offline scans deben reconciliarse con backend cuando vuelva conectividad

## 9.2 Policy rules

- una policy no puede mutarse retroactivamente; solo versionarse
- solo una versión activa por combinación de policy + owner + rango temporal aplicable
- decisiones históricas deben conservar snapshot de reglas

## 9.3 AI rules

- AI findings nunca son automáticamente “final truth”
- hallazgos críticos deben permitir manual review
- regulatory mapping debe depender de jurisdicción + policy version
- confidence score no reemplaza reasoned explanation

## 9.4 Reporting rules

- daily summaries deben consolidar access decisions + findings + unresolved risks
- export debe incluir timestamps y referencias de políticas/versiones
