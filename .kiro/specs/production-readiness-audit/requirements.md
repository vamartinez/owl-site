# Requirements Document

## Introduction

This spec is a Product Owner production-readiness audit performed by live-testing the deployed `dev` environment (admin portal at `localhost:3000` proxying `https://qhk659i3s9.execute-api.us-east-1.amazonaws.com/dev`, landing page at `localhost:5173`/`localhost:3001`), authenticated as a real `platform_admin` user, plus source-level root-cause verification for every confirmed defect, plus a competitive benchmark against SiteDocs, HammerTech, Procore, and Raken/SafetyCulture (iAuditor) — the closest analogs to this product's positioning as a BC construction compliance platform.

This is **not** a first pass. Two prior audits already exist and were partially executed:

- `.kiro/specs/admin-portal-audit-fixes` (7 bugs, marked 23/23 tasks complete)
- `.kiro/specs/admin-portal-audit-fixes/verification-notes.md` (an independent re-test that found 2 of those 7 "complete" tasks were not actually fixed, because CDK/API Gateway source changes were never deployed to `dev`)
- `.kiro/specs/admin-portal-audit-fixes-v2` (3 residual fixes from those verification notes, marked 12/12 complete)

Re-testing live today shows that v1 and v2 **did** move the product forward — the report-validation Lambda now exists in the API Gateway stack, the Site Profile and Sites list crash/bare-`%` bugs are gone, and the certification document viewer renders real S3 documents. But new residual issues and net-new defects were found in the same pages, plus the underlying business flow the product is supposed to be built around (self-service worker site access) has no implementation at all. This spec documents all of that in one place, ranks it by business impact, and adds the specific capability gaps found in the competitive benchmark, so Kiro has one prioritized backlog instead of three overlapping bug lists.

**Every defect below was reproduced live against the deployed `dev` environment on 2026-09-03 and traced to a specific file/line in the source**, not inferred from documentation. Where a finding could not be reproduced with full certainty (e.g. requires AWS CLI/CloudWatch access this session did not have), that uncertainty is stated explicitly in the requirement.

Two requirements were added after the initial audit pass at the Product Owner's explicit direction: Requirement 11 (Safety AI has no working way to submit evidence — found via direct live testing, not documentation) and Requirement 12 (migrate all AI inference from AWS Bedrock to the direct Anthropic Claude API, using the platform owner's own Anthropic credentials — an explicit architecture decision, not a defect).

## Glossary

- **Admin_Portal**: The React SPA at `packages/admin-portal`, the staff-facing web application (roles: platform_admin, tenant_admin, site_admin, supervisor, cso, gate_operator).
- **Landing_Page**: The public marketing site at `packages/landing-page`.
- **Backend**: The Lambda + API Gateway services at `packages/backend`.
- **Killer_Workflow**: The product's stated core loop (`ideas.txt`, §3): a worker scans a persistent QR code or opens an SMS link, the system validates identity/certifications/site policy with no staff involvement, and issues an explainable allow/conditional/deny decision — the workflow the product thesis depends on to be "sticky" and differentiated.
- **Report_Validation_Service**: The Lambda at `packages/backend/src/services/report-validation/handler.ts`, serving `/report-validation/*`, which backs the Admin Portal's `/reports` page.
- **Site_Service**: The site CRUD handlers (`handleListSites`, `handleGetSite`, ...) inside `packages/backend/src/services/policy/handler.ts`.
- **Admin_Users_Service**: `packages/backend/src/services/identity/admin-users.ts`, backing `GET /admin/users`.
- **Leads_Service**: `packages/backend/src/services/leads/handler.ts`, delegated to from `packages/backend/src/services/identity/handler.ts`, backing the public `POST /leads` endpoint used by the Landing Page contact form.
- **Stale_Deploy**: A state where a fix exists in source (CDK stack or Lambda code) but the `dev` AWS environment is still running an older build, because `pnpm build:backend && pnpm deploy:dev` was not re-run after the source change. Explicitly documented as having caused false "complete" markings in `admin-portal-audit-fixes`.

## Requirements

### Requirement 1: Every deployed frontend must actually be able to reach the API (P0 — revenue-blocking, and possibly blocks the entire Admin Portal in production)

**User Story:** As a prospective customer filling out the "Get Started Today" form on the Landing Page, I want my submission to be received, so that the sales team can follow up and the business can generate leads at all. As any staff user of the deployed (non-localhost) Admin Portal, I want the application to actually be able to call the API, so that the product functions at all outside of a developer's local machine.

#### Acceptance Criteria

1. WHEN a visitor submits the Landing Page contact form with valid `company_name`, `contact_name`, `email`, and `message`, THE Leads_Service SHALL return `201 Created` and the Landing Page SHALL show a success confirmation, not "Something went wrong. Please try again or email us directly."
2. **Root cause, confirmed definitively — this is NOT a backend bug.** Direct `curl` against the live API Gateway (`POST https://qhk659i3s9.execute-api.us-east-1.amazonaws.com/dev/leads`) with a correctly-shaped `{company_name, contact_name, email, message}` payload returns `201 {"success":true,"lead_id":"...",...}` — the backend works. Submitting the same form through the browser at `localhost:3001` fails because `packages/landing-page/src/components/ContactForm.tsx` line 70-71 does `const apiUrl = import.meta.env.VITE_API_URL || ''; fetch(\`${apiUrl}/leads\`, ...)`, and `VITE_API_URL` is never set to a real value at build time: `packages/landing-page/.env.local` has `VITE_API_URL=` (empty, and gitignored so it doesn't exist in CI anyway), and `.github/workflows/landing-page.yml`'s build step (`pnpm --filter landing-page build`) sets no environment variable before running Vite's build (which none of the three GitHub Actions workflows in this repo do — they only `lint` and `build`; none of them run `cdk deploy` or upload anything to S3/CloudFront, meaning **the actual deploy to AWS is a fully manual, undocumented-in-CI process today**, run from whatever `.env.local` happens to exist on the deploying developer's machine).
3. **This same defect class likely also affects the deployed Admin Portal, not just the Landing Page — flagged as HIGH confidence from source review, but NOT live-verified against the actual deployed CloudFront URL this session (only `localhost:3000` was tested, which uses Vite's dev-server proxy and therefore masks this exact bug).** `packages/admin-portal/src/services/api-client.ts` line 3 does `const API_BASE_URL = import.meta.env.VITE_API_URL || '/api';` — defaulting to the relative path `/api` when unset. `packages/admin-portal/.env.local` (gitignored, not present in CI) has `VITE_API_URL=/api` checked in locally, plus an unused `VITE_API_URL_DIRECT` variable that is defined but never referenced anywhere in source (dead config, likely a leftover from earlier debugging of this exact class of issue). Critically, `packages/backend/infra/lib/hosting-stack.ts`'s CloudFront distribution has only two S3 origins (admin portal bucket, landing page bucket) and **no `/api/*` behavior forwarding to API Gateway** — so even a correctly-relative `/api` path would 404 against the real deployed CloudFront domain, the same way `vite.config.ts`'s `server.proxy` (which DOES rewrite `/api` → the API Gateway, but only for the local `vite dev` server, never for a production build) is invisibly doing the work that makes local testing look fine.
4. THE fix SHALL do ALL of the following, for both `admin-portal` and `landing-page`: (a) inject the real API Gateway invoke URL as `VITE_API_URL` at build time in each package's GitHub Actions workflow (or whatever build step actually precedes the real S3/CloudFront deploy), reading it from a value CDK already knows (the API Gateway stack's own output URL) rather than hand-typing it; (b) as a more robust alternative or complement, add a CloudFront behavior in `hosting-stack.ts` that forwards `/api/*` to the API Gateway origin, so relative-path requests work in every environment without needing a build-time URL at all — Kiro SHALL evaluate which approach (or both) is more consistent with this codebase's existing patterns before implementing; (c) live-verify against the actual deployed CloudFront URLs (not `localhost`) that both the Landing Page contact form and at least one authenticated Admin Portal API call succeed end-to-end.
5. THE Landing Page SHALL distinguish between "temporary server error, please retry" and "validation error, fix your input" in its error message — the current generic "Something went wrong" gives a prospect no actionable next step besides emailing directly, which defeats the point of having a form.
6. THE fix SHALL add a lightweight CI or post-deploy smoke-test check (even a simple scripted `curl` against the live CloudFront URL after deploy) that fails loudly if the deployed frontend cannot reach the API, so this exact class of "looks fine in local dev, silently broken in every real deploy" defect cannot reoccur undetected — this is the same category of false-positive `verification-notes.md` already documented once for backend-only changes, now shown to apply to frontend deploys too.

### Requirement 2: Reports module must load for every role that has access (P0 — core product promise)

**User Story:** As a tenant_admin/CSO, I want to open Reports and see the list of compliance reports, so that I can review and export audit-grade evidence — the "audit-grade explainability" pillar this product is positioned on.

#### Acceptance Criteria

1. WHEN an authorized user (platform_admin, tenant_admin, site_admin, cso per `docs/ROLES.md`) opens `/reports`, THE Admin_Portal SHALL display the report list, not "Failed to load reports — API Error [400]: BAD_REQUEST".
2. **Root cause, confirmed by direct source comparison**: `packages/admin-portal/src/features/report-validation/hooks/useReports.ts` (line ~15) sends `sort_by` values `'created_at' | 'latest_validation_date'`. `packages/backend/src/services/report-validation/types.ts` (`listReportsQuerySchema`, lines 311-322) only accepts `sort_by` values `'upload_date' | 'validation_date'` via Zod `.enum(...)`. Every request's default `sort_by=created_at` fails schema validation, so `GET /report-validation/reports` returns `400 Invalid query parameters` on literally every page load, for every role, unconditionally.
3. THE fix SHALL make the `sort_by` (and `page`/`page_size` vs `limit`/`cursor` — see note below) contract identical between `useReports.ts` and `listReportsQuerySchema`, choosing one canonical set of names/values and updating whichever side is wrong (recommendation: keep the backend's `upload_date`/`validation_date` naming since it matches the underlying data model, and fix the frontend to send those values).
4. Separately, `useReports.ts` sends `page`/`page_size` while `paginationQuerySchema` (`packages/backend/src/shared/validators.ts`) expects `limit`/`cursor` (cursor-based pagination). This does not currently cause the 400 (both are optional with defaults), but it silently means **pagination is broken** — `page=2` requests will always return page 1's results. THE fix SHALL align these too, converting the frontend to cursor-based pagination or the backend to page-based, consistently with how every other paginated list endpoint in this codebase works.
5. This is a residual of `admin-portal-audit-fixes` Bug 5 / `admin-portal-audit-fixes-v2` Requirement 1: the routing/deployment problem verification-notes.md identified is now fixed (the Lambda and API Gateway resources exist and are reachable — confirmed by getting a schema-validation-shaped 400 instead of API Gateway's generic "Missing Authentication Token" 403). What's left is a plain frontend/backend contract mismatch that was never integration-tested end-to-end after the routing fix landed.

### Requirement 3: Site Profile detail page must display the site's actual data (P1 — residual, root cause now fully diagnosed)

**User Story:** As a site_admin, I want to open a site's profile and see its name, address, active worker count, compliance percentage, and assigned contractor, so that I can manage that site.

#### Acceptance Criteria

1. WHEN a user opens `/sites/{id}` for any valid site, THE Admin_Portal SHALL display that site's name and address in the page header. Live-verified today: the header renders blank (just a location-pin icon and a bare comma) for a site whose name and address display correctly on the `/sites` list page one click away.
2. **Root cause, confirmed by direct source comparison**: `handleListSites` (`packages/backend/src/services/policy/handler.ts`, ~line 594) returns a flat, mapped shape: `{ id, name, address, timezone, ... }`. `handleGetSite` (same file, ~line 609-631) returns `{ site: result.Items[0] }` — the **raw, unmapped DynamoDB item, nested one level deeper under a `site` key**. `SiteProfile.tsx` (line 63, 66) reads `data.name` and `data.address` directly (matching the list shape), so for the detail endpoint these are always `undefined`. THE fix SHALL make `handleGetSite` return the same flat, mapped shape as `handleListSites` (reusing the same mapping function), so `data.name`/`data.address` resolve correctly and no PK/SK/internal DynamoDB attributes leak to the client.
3. WHEN the Compliance, Active Workers, and Contractor stat cards are rendered on `/sites/{id}`, THE Admin_Portal SHALL continue to show "N/A" when the backend has no computed value (this guard already exists in `SiteProfile.tsx` and works correctly — do not regress it), but THE Site_Service SHALL actually compute and return real `activeWorkers`, `compliancePercent`, and `contractor` values for `handleGetSite`, the same way `handleListSites` already does not either — per `verification-notes.md`, a working per-site compliance calculation already exists in `handleComplianceSummary`'s `bySite` loop (`packages/backend/src/services/reporting/handler.ts`, ~lines 824-848) and SHOULD be extracted into a shared helper reused by both `handleGetSite` and `handleListSites`, rather than reimplemented twice.
4. THE fix SHALL NOT regress the crash-guard and bare-`%` fixes already verified working from `admin-portal-audit-fixes-v2` (empty `requiredCerts`/`recentActivity` arrays must continue to render empty states, not throw).

### Requirement 4: Users & Roles administration must list real tenant users (P1 — residual, blocks user/role management entirely)

**User Story:** As a platform_admin or tenant_admin, I want Users & Roles (`/admin`) to show the users in my tenant, so that I can invite users and assign roles — the only UI this platform has for that.

#### Acceptance Criteria

1. WHEN a platform_admin or tenant_admin opens `/admin`, THE Admin_Portal SHALL list at least the currently authenticated user, plus any other user in the same tenant. Live-verified today: the page loads without an error (this is progress — `verification-notes.md` recorded a 403 here previously, now fixed) but shows "0 users in the platform / No users found" while an authenticated platform_admin is actively using the page in that exact tenant.
2. **Likely root cause, needs live confirmation with AWS access this session lacked**: `listAdminUsers` (`packages/backend/src/services/identity/admin-users.ts`, line 83) filters Cognito's `ListUsersCommand` with `Filter: '"custom:tenant_id" = "${tenantId}"'`. AWS Cognito's `ListUsers` `Filter` parameter only supports a fixed set of standard attributes (`username`, `email`, `phone_number`, `name`, `given_name`, `family_name`, `preferred_username`, `cognito:user_status`, `status`, `sub`) — **custom attributes such as `custom:tenant_id` are not filterable this way**. THE fix SHALL either (a) call `ListUsersCommand` without the unsupported `Filter` and filter by `custom:tenant_id` in application code after fetching (acceptable at this user-pool scale), or (b) maintain a DynamoDB-backed user index synced from Cognito (post-confirmation trigger) that supports the tenant-scoped query natively. Kiro SHALL verify which failure mode is actually occurring (thrown `InvalidParameterException` vs. a Filter that silently matches nothing) before choosing the fix, since this session could not inspect CloudWatch logs.
3. THE "Invite User" action on this page SHALL be smoke-tested end-to-end once the list is fixed — it was not exercised in this audit because there is nothing to invite alongside (an empty list makes it unclear if invites land in the same tenant).

#### Acceptance Criteria

4. WHEN a worker's legal name is stored with literal surrounding quote characters (e.g. a record observed today rendering as `"Test"` in the UI, quotes included), THE Worker creation/update path SHALL trim and sanitize free-text name fields so stored values never include un-stripped quote characters from copy-pasted or JSON-like input.

### Requirement 7: A worker self-service site check-in flow must exist (P0 — the product's own stated core workflow is unbuilt)

**User Story:** As a construction worker arriving at a site, I want to scan a persistent QR code or open a link received by SMS, and have the system tell me (in under a few seconds, with no staff member needed) whether I'm allowed on site today, so that site access matches the product's own documented "killer workflow."

#### Acceptance Criteria

1. `ideas.txt` (§3, "Killer workflow del MVP") explicitly defines the MVP's central loop as: worker scans a persistent QR or receives an SMS link → the system validates identity/certifications/site policy **without staff involvement** → an explainable allow/conditional/deny decision is issued. Route-level review of `packages/admin-portal/src/app/router.tsx` shows no such route exists: the only access-control page is `/site-access` (`CheckIn.tsx`), which is a **staff-operated terminal** ("Enter Worker ID or scan badge" — a gate operator scans a worker's badge, not a worker scanning anything themselves).
2. `docs/API-ROUTES.md` confirms every `/access/*` route (`/access/request`, `/access/scan`, `/access/tokens`, ...) requires Cognito auth. There is no public, unauthenticated endpoint a worker's own phone could call to self-check-in — contrast with `/leads` and `/public/forms/:token`, which are the only two public routes in the entire API, and both serve unrelated features (marketing leads, contractor QR forms).
3. THE Backend SHALL expose a public (no staff Cognito session required) worker-facing check-in flow: a persistent per-worker or per-site QR/token that resolves to a mobile-friendly web page (reusing the `contractor-forms-qr` spec's proven pattern of a public UUID token + client-side QR generation, already implemented for contractor forms) where the worker identifies themselves (e.g. last 4 digits of phone + DOB, or a magic SMS link via the existing `notification-service`/SES+SNS integration) and receives an explainable allow/conditional/deny decision, consistent with `docs/ROLES.md`'s existing "worker/gate_operator sees only reasons and required actions" explainability rule.
4. THIS requirement is scoped as a new sub-spec to be broken out separately (it is a multi-day feature, not a bug fix) — this requirement's acceptance criterion for **this** spec is that Kiro produces a dedicated design/tasks breakdown for it (see `tasks.md` in this spec), not that it's implemented inline here.

### Requirement 8: UI language consistency (P2)

**User Story:** As any staff user, I want the entire Admin Portal to be in one consistent language, so that the product feels finished rather than half-translated.

#### Acceptance Criteria

1. WHEN a user navigates the Admin Portal, THE UI text SHALL be consistently in one language per the platform's target market (English, per every other module: Dashboard, Workers, Sites, Certifications, Safety AI, Incidents, Reports, Administration). Live-verified: the "Formularios" module (`/forms`, the `contractor-forms-qr` feature) is entirely in Spanish — "Formularios", "Crear Formulario", "Estado", "Publicado", "Borrador", "Cargando formularios...", "Duplicar" — with no language toggle and no relation to the user's own selected language.
2. THE fix SHALL either (a) translate the `contractor-forms-qr` feature's UI strings to English to match the rest of the platform, or (b) if multi-language support is an intentional future direction, implement a real i18n system (e.g. `react-i18next`) with an explicit language switcher, rather than having one module hardcoded to a different language than the rest of the app. Given no other module has any i18n infrastructure, (a) is the pragmatic near-term fix; (b) should be logged as a future roadmap item, not implemented ad hoc for one module.

### Requirement 9: Close the table-stakes gap against SiteDocs, HammerTech, Procore, Raken, and SafetyCulture (P1/P2 — competitive parity)

**User Story:** As the Product Owner, I want the platform to have the baseline capabilities every serious construction-safety competitor already ships, so that a prospective BC customer evaluating this against SiteDocs or HammerTech doesn't immediately disqualify it for missing something they consider standard.

#### Acceptance Criteria

1. **Real-time site headcount / emergency muster list.** HammerTech and SiteDocs both treat "who is physically on site right now" as a first-class, always-visible view (critical for fire/emergency evacuation accountability, not just an audit nicety). THE `/site-access` page currently shows only a "Recent Check-Ins" log (last 10 entries) with no live roster of currently-checked-in workers per site. THE Admin_Portal SHALL add a live "Workers currently on site" view, scoped per site, showing everyone checked in but not yet checked out.
2. **Digital signature capture for inductions/orientations/toolbox talks.** SiteDocs, HammerTech, and Raken all require a captured signature (finger/stylus on a touch device) as proof a worker completed a site orientation or toolbox talk, which becomes part of the audit trail. Nothing in the reviewed router (`Formularios`, `Incidents`, `Safety AI`) exposes a signature-capture UI. THE fix SHALL add signature capture as a field type available when building Formularios forms, at minimum, since that module already supports arbitrary field types (per `contractor-forms-qr` design).
3. **Photo annotation/markup on safety findings.** SafetyCulture and Procore let a reviewer draw arrows/circles/text directly on a hazard photo to point at the specific issue, both for the AI-detected finding and for human-added evidence. THE Safety AI Findings review flow (`/safety-ai`, `/safety-ai/pending-review`) was not tested with actual finding data in this audit (0 findings existed in `dev`); Kiro SHALL verify whether photo annotation exists at all, and if not, scope it as a follow-up (do not implement speculatively without confirming the gap first — reseed a finding via Task 7's data script and check).
4. **Corrective action loop with due dates and re-inspection.** All five competitors close the loop: a failed check/finding creates a corrective action, assigned to someone, with a due date, and the finding isn't resolved until a re-check confirms the fix. `/safety-ai/corrective-actions` exists as a route in this codebase; Kiro SHALL verify (same caveat as 9.3 — needs real finding data to test) whether it actually supports assignment + due date + re-inspection close-out, or is a read-only list.
5. **Certification/COR/D&A tracking depth.** SiteDocs' strongest BC/Alberta-specific differentiator is COR (Certificate of Recognition) audit support and drug & alcohol testing program tracking — both are common contractual requirements on BC industrial/oil-and-gas-adjacent construction sites, not just generic "certifications." THE Certifications module currently tracks generic type/issuer/expiry only (confirmed live: "Certifications by Type" shows one undifferentiated "Unknown" bucket for the one active cert in `dev`, per Requirement 5). This is flagged as a roadmap item for Kiro/product to scope, not a task to implement blind in this spec — it needs a product decision on whether COR/D&A support is in scope for the initial BC go-to-market.
6. **Offline-first mobile capture.** SiteDocs, HammerTech, Raken, and SafetyCulture all assume field workers/supervisors are on a jobsite with poor or no connectivity and build offline-first data capture with background sync as core architecture, not an add-on. This codebase already has a `sync-service` Lambda and `/sync/*` routes (`docs/API-ROUTES.md`) suggesting offline sync was designed for, but the Admin Portal itself is a standard online-only React SPA with no service worker/offline queue visible in `router.tsx`/`providers.tsx`, and there is no mobile app or PWA manifest in `packages/admin-portal`. Given Requirement 7 already scopes a net-new mobile-friendly public worker flow, Kiro SHALL evaluate whether that follow-up spec (`worker-self-checkin`) should be offline-tolerant from the start (e.g. service worker + local queue for the check-in submission itself), since retrofitting offline support later is significantly more expensive than designing for it up front — this is a design decision for that spec, not an implementation task here.
7. **Customizable inspection template library.** SafetyCulture's biggest UX differentiator is a large public library of pre-built, customizable inspection templates so a new customer never starts from a blank form. THE Formularios module already supports building custom forms (per `contractor-forms-qr`); Kiro SHALL evaluate — as a lightweight product/content task, not engineering — whether shipping 5-10 pre-built BC-relevant templates (daily hazard assessment, toolbox talk sign-off, PPE inspection, incident report, subcontractor orientation) as starter content would meaningfully improve time-to-value for a new tenant, since the underlying form-builder engineering already exists.
8. **Push/SMS notifications for expiring certifications.** SiteDocs markets automatic expiry alerts as a headline feature. THE Dashboard already has a "Certs Expiring (30d)" KPI card (confirmed live, currently showing 0), implying the data model supports this; Kiro SHALL verify whether an actual notification (email/SMS via the existing `notification-service`) fires when a certification crosses the 30-day threshold, or whether the KPI card is display-only with no proactive alert — this determines whether it's a small wiring task or already done.

None of the sub-items in this requirement are pre-scoped as implementation tasks with file-level detail the way Requirements 1-8 are, because they require a product decision (which gaps matter for the initial BC launch) and, in several cases (9.3, 9.4, 9.8), a verification step this audit could not complete due to empty `dev` data. `tasks.md` scopes this requirement as an investigation-and-prioritization task, not blind implementation.

### Requirement 10: Backend deploy/verify discipline (process requirement, applies to every fix in this spec)

**User Story:** As the Product Owner, I don't want to re-litigate the same "looks fixed in source but isn't deployed" false-positive that `verification-notes.md` already documented once for this exact codebase.

#### Acceptance Criteria

1. BEFORE marking any task in this spec's `tasks.md` complete, Kiro SHALL run `pnpm build:backend && pnpm deploy:dev` (or the equivalent targeted stack deploy) and re-test the live `dev` environment for that specific fix — not just confirm the source diff looks correct.
2. Given Requirement 1 (leads 503) may resolve on redeploy alone with no code change needed, THE first task in this spec's implementation plan SHALL be a full `dev` redeploy and a fresh re-test pass of every P0/P1 item in this document, to separate "genuinely broken" from "fixed in source, never deployed" before any further code is written.

### Requirement 11: Safety AI must have a way to actually submit evidence for analysis (P0 — the flagship AI pillar has no entry point)

**User Story:** As a supervisor, site_admin, or cso, I want a visible, working control to upload a jobsite photo and have it analyzed for safety hazards, so that the "AI-assisted safety observation" pillar this product is positioned on can be used at all.

#### Acceptance Criteria

1. WHEN a user with photo-upload permission per `docs/ROLES.md` (platform_admin, tenant_admin, site_admin, supervisor, cso) opens `/safety-ai`, THE Admin_Portal SHALL display a visible, functional control (button, drag-and-drop zone, or equivalent) that lets the user select or capture a photo and submit it for AI hazard analysis. ### Requirement 12: Replace AWS Bedrock with the direct Anthropic Claude API for all AI inference (explicit product-owner architecture decision)

**User Story:** As the Product Owner, I want every AI feature in this platform to call Claude directly through the Anthropic API using our own API credentials, instead of through AWS Bedrock, so that we control model access, billing, and versioning directly rather than through Bedrock's provisioning/quota layer.

#### Acceptance Criteria

1. THE codebase currently invokes Bedrock (via `@aws-sdk/client-bedrock-runtime` and/or Bedrock Knowledge Bases) in at least four places: `packages/backend/src/services/detection/detector.ts` (Safety AI PPE/hazard detection from photos, via `BEDROCK_MODEL_CONFIG.modelId`), `packages/backend/src/services/scene-understanding/classifier.ts` (scene classification, via `SCENE_BEDROCK_MODEL_CONFIG.modelId`), `packages/backend/src/services/report-validation/validation-engine.ts` (RAG-based compliance validation via Bedrock Knowledge Base `RetrieveAndGenerate` against a hardcoded `anthropic.claude-3-5-haiku-20241022-v1:0` model ARN), and `packages/backend/src/services/report-validation/kb-manager.ts` (Knowledge Base document sync). THE not-yet-started `worksafebc-pdf-compliance-agent` spec (0/56 tasks) is also designed around Bedrock per its `design.md` and SHALL be updated to target the direct API before implementation begins, so it isn't built against the wrong provider from day one.
2. THE fix SHALL replace every Bedrock Runtime `InvokeModel`/`Converse` call (vision-capable, for `detection`/`scene-understanding`) with the equivalent call to the Anthropic Messages API (`https://api.anthropic.com/v1/messages`) using the official `@anthropic-ai/sdk` package, authenticated with an `ANTHROPIC_API_KEY` stored in AWS Secrets Manager and injected into the relevant Lambdas' environment by CDK — following the same pattern this codebase already uses for other sensitive configuration (env vars injected by CDK per the README), not a hardcoded key.
3. THE RAG pipeline currently provided by Bedrock Knowledge Bases + S3 Vectors (`report-validation`) has no Bedrock-free drop-in replacement, since retrieval-augmented generation is a Knowledge Base capability, not a plain model-invocation capability. Kiro SHALL evaluate and choose one of: (a) load the full regulatory corpus (WorkSafeBC OHS Regulation, BC Building Code, Construction Safety Standards) directly into the Claude API request using prompt caching (Anthropic's `cache_control` on large static context blocks), which is architecturally simpler and removes the Knowledge Base/S3 Vectors dependency entirely if the corpus fits within Claude's context window with room for the user's document; or (b) stand up a lightweight self-managed vector store (e.g. pgvector, or a simple embeddings index) queried before calling the Claude API directly. Given this codebase already prefers simplicity and this corpus is a small, well-defined regulatory set (not open-ended web-scale retrieval), option (a) SHALL be the default recommendation unless the actual corpus size makes it infeasible — Kiro SHALL measure the corpus's token count before deciding.
4. THE fix SHALL preserve every existing behavior contract: response shapes, confidence scores, finding structure, and the `model_version` field already recorded on findings (currently populated from `BEDROCK_MODEL_CONFIG.modelId`/`SCENE_BEDROCK_MODEL_CONFIG.modelId`) SHALL continue to be populated, now reflecting the direct Anthropic API's model identifier instead.
5. THE fix SHALL remove Bedrock-specific IAM permissions, Knowledge Base CDK resources, and S3 Vectors provisioning that become unused once the migration completes, rather than leaving orphaned infrastructure — Kiro SHALL confirm via `cdk diff` that only the intended resources are removed.
6. THE fix SHALL NOT be implemented speculatively inline in this spec — given it touches four+ Lambda services, CDK infrastructure, and a not-yet-started spec, THE first task for this requirement SHALL be scoping a dedicated follow-up spec (`.kiro/specs/ai-provider-migration` or similar), following the same "scope now, implement separately" pattern already used for Requirement 7 (worker self-check-in) in this document.
